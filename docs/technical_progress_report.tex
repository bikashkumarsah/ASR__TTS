\section{Workflow Architecture}
\begin{enumerate}[leftmargin=1.7em]
\item \textbf{Extract:} Stream source files, split text into sentences, filter quality, deduplicate normalized text, and write chunked JSONL pool files.
\item \textbf{Annotate:} Add tense, polarity, gender, and sector labels to every pool chunk.
\item \textbf{Select:} Stream annotated chunks, retain a bounded candidate reservoir for each metadata cell, and select the next balanced batch.
\item \textbf{Analyze:} Write a batch report with metadata distributions and syllable statistics.
\item \textbf{Merge:} Deduplicate selected batch records and write the final corpus JSONL file.
\end{enumerate}

\subsection{Memory-Safety Improvement}
\textbf{Problem.} The original selection path read every \texttt{pool\_chunk\_*.jsonl} file into one Python list.
On a large cloud run this attempted to materialize all 2,031 pool chunks and created an unnecessary RAM demand.
\textbf{Implemented solution.} Selection now streams every pool chunk and uses reservoir sampling to retain only a bounded number of candidates per metadata cell.
The default is 2,000 candidates per cell, configured with \texttt{--max-candidates-per-cell}; the complete pool is no longer held in memory during selection. The observed 100k run used at most about 10 GB of a 120 GB cloud instance, leaving room to increase this bounded cap for wider coverage candidate choice.
In multi-worker mode this is a global per-cell cap: the allowance is divided between workers and chunk files are interleaved, preventing the cap from multiplying by the worker count.
\subsection{Cloud CPU Scaling Improvement}
The pipeline accepts \texttt{--workers} and defaults to all CPU cores visible to Python.
The recommended cloud invocation is:
\begin{verbatim}
CLOUD_WORKERS="$(nproc)"
python -m dataset_builder.pipeline run-batch \
  --batch-id 1 --target-size 5000 --max-corpus 0 \
  --max-chunks 0 --workers "$CLOUD_WORKERS"
\end{verbatim}
Parallel Parquet extraction, hash-partitioned deduplication, chunk writing, annotation, streaming, and selection use this worker allocation.
The previous 32-worker cap in the extraction merge phase was removed. A one-worker path is available for low-memory or interactive-notebook execution.
\subsection{Workflow Reliability Improvement}
Partial annotation can bias metadata selection. The pipeline now checks pool chunks without materializing the pool and stops with a clear error if annotation is incomplete.
Annotation processes sequentially when one worker is requested, avoiding a macOS/interpreter process-spawn issue in interactive sessions.

\section{Known Constraints and Operating Guidance}
\begin{itemize}[leftmargin=1.7em]
\item The full source corpus is large. Download only the final corpus, cumulative state, and reports unless a resume is required.
\item Full-core operation increases throughput, while each worker keeps a bounded reservoir. The cap is global rather than per worker; increase \texttt{--max-candidates-per-cell} to widen coverage choice, or reduce it/use \texttt{--workers 1} if RAM is constrained.
\item Distribution reports describe the selected corpus; they do not replace qualitative ASR-data review or audio/text alignment validation.
\item Retain the cloud pool. Re-extraction and re-annotation are unnecessary for the planned coverage-improvement run.
\item Per-batch coverage is not aggregate coverage. The 100k cloud state establishes a 57.35\% aggregate coverage baseline; use it for the next-run comparison.
\item The observed 10 GB peak at a 2,000-candidate cap does not justify allocating all 120 GB. Python worker and merge peaks vary with record size; begin the next run at 8,000 candidates per cell and retain at least half the instance memory as headroom.
\item If a batch fails after a prior batch completes, do not reset the corpus. Pull the current code and rerun only the failed batch; the state file preserves previous selections.
\end{itemize}
\section{Next Run: RAM-Scaled Coverage Improvement Using the Existing Cloud Pool}
The next run should reuse the existing annotated cloud pool rather than rebuilding it. The objective is to use a wider bounded reservoir to select sentences containing the 760 uncovered and low-frequency lookup syllables while maintaining practical metadata balance.
\begin{enumerate}[leftmargin=1.7em]
\item \textbf{Preserve the current result.} Copy the current 100k corpus, state, and reports to a baseline directory before extending the active state with new batches.
\item \textbf{Reuse the cloud pool.} Use the already extracted and annotated \texttt{asr\_corpus/pool/} chunks. Do not run \texttt{reset} and do not use \texttt{--force-extract}.
\item \textbf{Build the coverage inventory.} Use the cloud \texttt{corpus\_state.json} syllable-frequency table to identify the 760 uncovered lookup syllables and the least frequent covered syllables. This is the baseline for the next run.
\item \textbf{Increase bounded candidate choice.} Run the first new batch with \texttt{--max-candidates-per-cell 8000}, four times the default 2,000-cap reservoir. Keep \texttt{--workers "\$(nproc)"}. If the observed peak remains below approximately 60 GB, raise the cap to 12,000 for subsequent completed batches; otherwise retain 8,000 or lower it.
\item \textbf{Prioritize coverage.} Target the 760 uncovered syllables first, then the least frequent covered syllables. Use \texttt{--coverage-priority 16}, which gives a stronger bonus for each as-yet unseen syllable while retaining the existing metadata stratification.
\item \textbf{Keep metadata guardrails.} Retain the tense, polarity, gender, and sector stratification as a constraint, but relax it only for cells that lack candidates containing the target syllables.
\item \textbf{Run coverage batches.} Run batches 21--30 with the chosen candidate cap, then merge to \texttt{corpus\_150k\_coverage.jsonl}. Do not change the cap during an in-progress batch; changing it between completed batches is safe.
\item \textbf{Measure improvement.} Record coverage, number of newly covered syllables, CV, metadata distributions, RAM peak, and the overlap with the 100k baseline after every batch. A proposed acceptance target is at least 65\% lookup coverage (1,159 of 1,782 syllables) without a material loss of metadata balance.
\end{enumerate}
The coverage-priority mode and configurable bounded reservoir are implemented. The expanded result should be merged to a new \texttt{corpus\_150k\_coverage.jsonl} file, while the backed-up 100k corpus remains the control dataset.
